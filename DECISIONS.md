# Architecture Decisions

## ADR-001: Monorepo Layout

DocuMind uses a single repository with `client/` for React and `server/` for Express. This keeps local development simple while still allowing independent deployment.

## ADR-002: Server Foundation Before Features

The first implementation phase creates configuration validation, database connection handling, health checks, logging, and centralized error handling before auth, uploads, AI, payments, or UI feature work.

## ADR-003: Express 4 For MVP Stability

The MVP pins Express to the 4.x line to match the original project tech stack and avoid framework migration risk during the initial build.

## ADR-004: AI Context Is Stored In The Repository

Copilot instructions, prompts, agents, skills, and compact AI context documents live in the repository so agent behavior is repeatable across sessions.

## ADR-005: Refresh Token Rotation

Authentication uses short-lived JWT access tokens returned in response bodies and longer-lived refresh tokens stored only in HttpOnly cookies. The database stores SHA-256 hashes of refresh tokens, not raw refresh tokens. Every refresh request rotates the token. If a previously rotated token is reused, all stored refresh tokens for that user are revoked.

## ADR-006: Google Login Verification

Google login accepts a Google ID token from the frontend and verifies it server-side with `google-auth-library` against `GOOGLE_CLIENT_ID`. Only verified Google email payloads can create or link accounts.

## ADR-007: PDF Uploads Are Temporary Ingestion Files

DocuMind does not permanently store uploaded PDF binaries in Phase 3. Multer writes each upload to a temporary local directory, the server validates and extracts text, then deletes the temporary file whether extraction succeeds or fails. MongoDB stores document metadata and extracted text for later viewing, summarization, and chat.

## ADR-008: Maintained `pdf-parse` Parser

The backend uses `pdf-parse` 2.x because the older 1.1.x parser rejected valid PDFs generated by common tooling with XRef parsing errors. The extraction service uses the `PDFParse` class and releases parser resources after every extraction.

## ADR-009: AI Provider Abstraction

DocuMind calls the OpenAI Responses API through a small provider abstraction. Production uses the official `openai` SDK, while tests inject deterministic providers. This keeps tests fast, avoids real API cost, and lets the code verify truncation, quota, SSE, and abort behavior without network dependencies.

## ADR-010: SSE For Document Chat

Document chat uses Server-Sent Events over HTTP instead of WebSockets. The flow is one-way during generation, so SSE is simpler and fits the streaming response shape. The stream emits `ready`, `chunk`, `done`, and `error` events.

## ADR-011: Server-Side AI Quota And Context Bounds

AI usage is counted server-side before model calls. Free users have a daily request quota and Pro users are counted without quota enforcement. Document text and chat history are truncated by configuration before calling the model to control cost and avoid unbounded context growth.
